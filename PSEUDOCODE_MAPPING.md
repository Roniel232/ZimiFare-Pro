## Additional technical protections

- SQLite `BEGIN IMMEDIATE` transactions guarantee that updating a ride, writing its payment and deducting a fare-card balance happen together or are all rolled back.
- A `UNIQUE` partial index on payment transactions' `ride_id` independently prevents duplicate recorded fare settlements.
- `FRAUD_THRESHOLD_CENTS = 5_000_000` and money parsing uses `Decimal`, avoiding float calculations for financial amounts.
- `tests/test_core.py` checks 15 scenarios, including concurrent card-versus-cash settlement where exactly one payment is accepted.

## Explicit changes or omissions

The pseudocode describes **a single-process, in-memory, single-session prototype**, whereas this implementation uses SQLite to permit shared state across local or simultaneous browser sessions. The currency was unspecified; the app chooses **JMD** for demonstration. An unpaid ride's unlinked `transactionID = 0` is represented by SQL `NULL`. Passwords are hashed and there is an extra current-password confirmation when changing one's own password. This is not a booking, GPS dispatch, SMS, real-money payment or full production platform; those capabilities are outside the supplied pseudocode.

### Additional administrator provisioning (implementation extension)
The pseudocode creates only the first trusted administrator. To support a group project with multiple administrators, the Streamlit **Manage users → Create administrator** tab adds more accounts after a signed-in active administrator re-authenticates with their own password. Public registration remains restricted to passenger/driver roles. This is an extension, not an original pseudocode requirement.

## Additive ZimiFare Pro implementation extensions

The supplied 32-page pseudocode uses integer IDs and does **not** prescribe
formatted IDs, transaction charts, CSV exports or visual animation. These are
presentation/reporting features built on top of the documented procedures:

- `zimifare/identifiers.py`: stable structured public references derived from
  the existing user, ride and transaction IDs. SQLite foreign keys are unchanged.
- `zimifare/analytics.py`: UTC-date/type/method filters and summaries of actual
  successful transactions. Top-ups and fare payments remain distinct.
- `ZimiFareStore.admin_list_rides`: administrator-authorized read-only report.
- `app.py:admin_analytics`: filters, KPI cards, Altair charts, CSV and ride ledger.
- `app.py:moving_car`: original decorative inline SVG with CSS movement and
  reduced-motion accessibility support; no business rules changed.
- `ZimiFareStore.create_administrator`: previously supplied controlled additional
  admin creation using the authorising admin's password.

Core rules from SettleRide, TopUpFareCard, ActiveUser, DetectFraud and the
integer-cent monetary contract remain enforced by the original service layer.
